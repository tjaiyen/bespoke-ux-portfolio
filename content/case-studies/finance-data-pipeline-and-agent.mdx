## Problem

Month-end close asks the same three questions every cycle: which accounts moved, are the
moves material, and why. The first two are arithmetic. The third is judgment — and it is
where the days go, because answering it means tracing a number back through systems that
were not built to be traced through.

That third question is also where a language model looks irresistible. It reads like a
writing task. The trap is that it is not: the narrative is only worth anything if the
numbers underneath it are correct and someone can check them.

## The constraint

The problem definition is first-hand rather than researched — I worked these closes. What I
brought to the design from that experience is one constraint, and it is the constraint the
entire architecture rests on:

**A variance explanation that cannot be traced back to a tested number is worse than no
explanation at all, because it will be believed.** Somebody signs off on those figures.

That single line decides the boundary. It is not a preference about model quality; it holds
even if the arithmetic is perfect, because the problem is auditability, not accuracy.

## Trade-offs

The architecture that demos best is the one where you hand the model the ledger and ask
what happened. I rejected it.

What shipped puts a hard line through the middle: tested dbt models produce every number
and carry the assertions; Airflow owns scheduling and recovery per model, so a failure is
recoverable rather than a rerun-everything event; the language model writes the narrative
and flags exceptions and touches none of the maths.

## The interesting part: what happens when the model is wrong

Drawing a boundary is easy to claim and easy to leak. The part of this I would actually
defend in a review is the layer that enforces it — `run_guardrails`, which sits between the
model's output and anything a human reads, and whose job is to fail loudly rather than ship
a wrong report.

It rejects four distinct failure modes, and the first two are the ones that matter:

1. **Hallucinated account.** Every account the model references must exist in the computed
   variance set. A narrative about an account that is not in the data is not a minor error —
   it is the exact failure that destroys trust in the whole tool, and it is the one an LLM
   makes most fluently.
2. **Missed material variance.** Every variance flagged material by the tested models must
   be addressed in the output. This one catches the *quiet* failure: a report that is
   entirely accurate about the things it mentions, and silently omits the item that mattered.
   Hallucination is loud; omission is not, which is why it needs a machine to catch it.
3. **Invalid direction** — must be `favorable`, `unfavorable` or `neutral`.
4. **Malformed schema** — a missing narrative or a non-list of exceptions.

The design decision underneath is a product decision, not an engineering one: **when the
model produces something unverifiable, the system refuses rather than degrades.** No
partial report, no "best effort" narrative with a caveat. A finance tool that sometimes
emits an unchecked number has no usable failure mode — you cannot ask a controller to
guess which reports to trust.

Coverage checking is the piece I would keep if I could keep only one. It is the difference
between "the model did not lie" and "the model did not leave anything out", and only the
second is what a close actually requires.

## Outcome

Seven runnable projects, and the thing that matters most about them is that you do not have
to take my word for any of it. The repository is public, the site is live, and the whole
system runs on a clean clone in about a minute:

```bash
git clone https://github.com/tjaiyen/tj-finance-portfolio
cd tj-finance-portfolio/dbt_finance_variance
pip install dbt-duckdb && dbt build     # PASS=14  ERROR=0
```

That is the entire argument. Not a screenshot of a dashboard, not a claimed metric — a
command a reviewer can run. The same command runs in CI on every push, so the number is not
a memory of one good day; the most recent run logs `PASS=33` and `PASS=14` with `ERROR=0`
across the two dbt projects.

## Retrospective

**The interface is the weakest part and I would invest there next.** The reasoning and the
guardrails are sound; the sandbox that exposes them is functional rather than considered.
Someone arriving at the live site has to already understand variance analysis to see why
the boundary between tested numbers and generated narrative is the interesting decision.
That is a design failure, not a documentation one — the architecture's best idea is
currently legible only from the code, which is precisely the criticism I would level at
someone else's project.

**The guardrails are asserted, not adversarially tested.** They reject the four failure
modes above because I wrote them to. What I have not done is run a deliberately misbehaving
model against them at volume to find the fifth mode I did not think of — a narrative that
references only valid accounts, covers every material variance, and is still misleading in
its framing. Coverage and existence are checkable; emphasis is not, and I do not currently
have an answer for it.

**The materiality threshold is a parameter, and parameters are where judgment hides.**
Whoever sets it decides what the report is allowed to omit. Right now it is passed in
rather than reasoned about, and a serious version of this would make that number a
first-class, visible, auditable part of the output rather than a configuration detail.
