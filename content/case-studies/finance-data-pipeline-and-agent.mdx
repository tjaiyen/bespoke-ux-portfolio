## Problem

Month-end close asks the same three questions every cycle: which accounts moved, are the
moves material, and why. The first two are arithmetic. The third is judgment — and it is
where the days go, because answering it means tracing a number back through systems that
were not built to be traced through.

That third question is also where a language model looks irresistible. It reads like a
writing task. The trap is that it is not: the narrative is only worth anything if the
numbers underneath it are correct and someone can check them.

## Research

The problem definition is first-hand rather than researched — I worked these closes. What
I brought to the design from that experience is one specific constraint, and it is the
constraint the entire architecture rests on:

**A variance explanation that cannot be traced back to a tested number is worse than no
explanation at all, because it will be believed.** Somebody signs off on those figures.

That single line decides the boundary. It is not a preference about LLM quality; it holds
even if the model's arithmetic is perfect, because the problem is auditability, not
accuracy.

## Trade-offs

The architecture that demos best is the one where you hand the model the ledger and ask
what happened. I rejected it.

What shipped puts a hard line through the middle: tested dbt models produce every number
and carry the assertions; Airflow owns scheduling and recovery per model, so a failure is
recoverable rather than a rerun-everything event; the language model writes the narrative
and flags exceptions and touches none of the maths.

The cost I accepted: the system cannot answer a question its models were not built for. A
genuinely novel "why" requires writing a new tested model, not a better prompt. That is
slower, and it is the right trade — the alternative degrades silently and surfaces at
audit, which is the most expensive place to find it.

## Outcome

Six runnable projects, and the thing that matters most about them is that you do not have
to take my word for any of it. The repository is public, the site is live, and the whole
system runs on a clean clone in about a minute:

```bash
git clone https://github.com/tjaiyen/tj-finance-portfolio
cd tj-finance-portfolio/dbt_finance_variance
pip install dbt-duckdb && dbt build     # PASS=14  ERROR=0
```

That is the entire argument. Not a screenshot of a dashboard, not a claimed metric — a
command a reviewer can run. The same command runs in CI on every push, so the number is not
a memory of one good day; the most recent run logs `PASS=14 WARN=0 ERROR=0`.

## Retrospective

The interface is the weakest part and I would invest there next. The reasoning and the
guardrails are sound; the sandbox that exposes them is functional rather than considered,
and someone arriving at the live site has to already understand variance analysis to see
why the boundary between tested numbers and generated narrative is the interesting
decision. That is a design failure, not a documentation one — the architecture's best
idea is currently legible only from the code.
