## Problem

A finance tool is adopted or rejected on one question, and it is not "is this accurate". It
is **can the person whose name goes under this number defend it.** Accuracy is necessary and
nowhere near sufficient — a correct number nobody can trace is, in a close, indistinguishable
from a wrong one.

Now build twenty-six of them. Standard-cost validation, margin-leak recovery, vendor
scoring, borrowing-base eligibility, food-safety traceability, earned value, yield and mix
variance, AP three-way match. Each one is a small deterministic tool over its own domain data,
and each one has the same trust problem.

Solve it twenty-six times and you have twenty-six different reliability stories. A
reviewer cannot form a view of the engine; they have to audit every tool separately, and the
weakest one sets the trust level for all of them.

## Why this is a design-system problem

A design system exists because consistency cannot survive being everyone's individual
responsibility. Buttons do not drift because someone reimplements a button badly; they drift
because reimplementing one is *available*.

The same logic applies to correctness, and that reframing is the whole design:

**The primitives that make a number defensible must be shared infrastructure, not a
convention each tool is trusted to follow.**

Not a utility library a tool imports when convenient. A kernel — so that "can this be traced"
has exactly one answer across the engine, and adding tool twenty-seven inherits the answer
instead of re-litigating it.

## What the kernel actually guarantees

Four primitives do the real work.

**Grounding — `narrative_verify`.** A narrative draft, from any language model, is decomposed
into atomic numeric and directional claims. Each claim is verified against the deterministic
tool output that produced the figures. An unsupported claim is **flagged inside the grounded
text — never silently removed.** That last part is the design decision: quietly deleting a
bad claim produces a clean-looking narrative that hides the fact the model drifted. Leaving
the flag visible tells the reader the model overreached *here*, which is information they
need.

**Reproducibility — `as_of`.** Every result carries four hashes: the input data, the metric
definitions, the tenant config, and the code. A number is not reproducible because someone
remembers how it was produced; it is reproducible because all four inputs are pinned. If any
one changes, the signature changes, and the difference is attributable rather than mysterious.

**Provenance — `attestation`.** The as-of signature is wrapped in an in-toto statement inside
a DSSE envelope and signed with ed25519. The choice of asymmetric signing over a shared-secret
MAC is deliberate: **a third party holding only the public key can verify who produced a
number and that it was not altered, and cannot forge one.** With an HMAC, the verifier holds
the same secret as the signer — which makes it a check between parties who already trust each
other, and that is not what an auditor needs.

**Injection boundary — `injection_guard`.** Untrusted free text — vendor names, memo lines,
document fields — is treated as data, never as instructions. In a finance engine, that text
arrives from suppliers and scanned documents, which is precisely the surface an attacker
controls.

## Where the kernel deliberately stops

The harder judgement was not what to share. It was what to leave alone.

A design system that abstracts everything stops being a system and becomes a framework you
have to defeat. The interesting work was drawing the line and then **writing down why it sits
there** — the same discipline as documenting why a component takes a variant instead of a
one-off override.

The lineage layer shows the same restraint. It emits spec-shaped OpenLineage events so a
standard collector or an auditor can consume a column-level provenance graph — and the
collector itself is **explicitly not built**. Naming a deferred boundary is worth more than a
half-built version of it that implies more coverage than exists.

## Outcome

Twenty-six components run on the kernel, with **772 pytest cases and 321 dbt tests green**
(`ERROR=0`) — re-run and counted directly for this study rather than quoted from an older
number. The output is published as a live operations dashboard, and every figure on it comes
from a real deterministic run of the underlying tool against synthetic sample data — nothing
is composed for display:

**[tjaiyen.github.io/tcf-finance-dashboard](https://tjaiyen.github.io/tcf-finance-dashboard/)**

Being straight about what you can check: **the engine repository is private.** The dashboard
is the artefact you can open, and the numbers above are from its own status line rather than
my recollection. If that is not enough evidence for a given claim, treat the claim as
unverified — that is the standard the rest of this portfolio holds itself to and this study
should not get an exemption.

## What this does not solve

**A verified claim can still be a misleading one.** `narrative_verify` checks that every
numeric and directional claim is supported by the deterministic output. It cannot check
emphasis. A narrative can be entirely grounded, cover every material item, and still lead
with the wrong one. Grounding and coverage are mechanical; salience is judgement, and I do
not have a mechanism for it.

**The kernel raises the floor, not the ceiling.** It guarantees a number is traceable,
reproducible and attributable. Whether the number is the *right* number for the decision at
hand is a modelling question the kernel never touches — and it would be a comfortable
mistake to read a green attestation as a statement about relevance.

**Signed provenance is only as good as key custody.** ed25519 gives a third party real
verification, and that is the correct primitive. It also moves the trust problem to who holds
the private key and how it rotates, which in a real deployment is an operational design
problem I have specified rather than solved.
