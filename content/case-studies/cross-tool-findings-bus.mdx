## Problem

A prioritization interface over many small, correct tools is only as honest as what feeds
it. The engine's cross-tool synthesizer already does the hard part well: it takes a
findings feed, asks a language model only to rank and narrate, and runs two deterministic
guardrails against the model's own output — every critical-severity finding has to be
referenced by some recommendation, and the top-ranked recommendation has to cite a finding
whose severity actually is the worst in the set. Neither check trusts the model's words;
both check the model's ranking against the severity the *feed* already carries.

What the feed is, right now, is a fixture. Fourteen tools in the engine have already,
independently, verified their own findings — but they were built with zero interface
uniformity between them, and the fixture is a hand-curated snapshot of what those fourteen
tools would say if something read them uniformly. Nothing in it is fabricated: every dollar
figure and severity traces to a real assertion elsewhere in the engine. But *as a live
system*, the feed does not exist, and the module's own source says so directly rather than
implying it works.

## The detail a live aggregator would have to get right

One fixture row is not a data point, it's a design constraint. A borrowing-base checker
flags an unpaid grower invoice as **critical**, even though the dashboard's own severity
rule for that check is magnitude-only — it would call the same row a lower "warning,"
because the dollar amount involved doesn't cross the rule's own threshold. The override
exists because the exposure is a PACA statutory trust claim, a category of risk that a
magnitude rule was never built to see.

That is the whole argument for why this is worth designing before it's worth building. A
generic aggregator that reduces every tool's finding to "a severity string and a dollar
number" would flatten that override the first time it ran — not through a bug, but through
its own normalization doing exactly what normalization does. The interface layer already
protects this: `run_guardrails` checks the model's ranking against the feed's own severity,
never the model's opinion of it. An aggregator that fed it anything less than each tool's
real, already-computed severity would quietly disable a guardrail that reads as intact.

## Outcome

Nothing here was built, so there is no outcome to report — only a stated design and what
would falsify it. The interface and its guardrails already exist and are exercised by
twenty-one passing tests today, re-run directly for this study; what's missing is only the
adapter layer that would feed them from something other than a hand-curated file. The
concept's actual claim is narrow: an adapter is worth building once there are enough
onboarded tools that hand-curating the feed becomes the bottleneck, and it should be built
as fourteen small translators into a shared shape, not one function that re-derives
judgment the tools already made correctly.

**What would falsify this:** if a tool's severity turned out to need re-interpretation at
aggregation time — for instance, two tools disagreeing about whether the same underlying
condition is critical — a per-tool adapter can't resolve that; only a cross-tool policy
layer could, and that is a different, harder project than the one described here.

## Where this would break

**The one-directional guardrail argument only holds if every tool's severity is trustworthy
on its own.** The design above assumes each tool already computed the right severity and
the aggregator's only job is not to disturb it. If a tool's own severity logic turns out to
be wrong in some case, an adapter that faithfully preserves it faithfully preserves the
mistake — this concept has no mechanism for catching an error at the source, only for not
introducing a new one downstream.

**Fourteen adapters is a floor, not a ceiling.** The engine has more tools than the
fourteen the synthesizer currently reads from; a real build would need to decide whether
every tool eventually gets a findings adapter, or whether some tools' output was never
meant to feed a cross-tool feed at all. That scoping question is unanswered here, and I
would not want to guess at it without seeing which tools actually produce anything worth
prioritizing across.
